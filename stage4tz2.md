# ТЗ №2. Levels Builder

## 1. Цель этапа

Реализовать построение и обслуживание ценовых уровней отдельно для Binance и Bybit.

Физически должны работать два контейнера:

```text
paper-levels-binance
paper-levels-bybit
```

Использовать одну кодовую базу и один Docker-образ с параметром:

```text
EXCHANGE=BINANCE
EXCHANGE=BYBIT
```

Каждый контейнер работает только со своей биржей.

---

# 2. Предварительная проверка

Перед изменением кода:

1. Прочитать:

   * `README.md`;
   * `docs/architecture/SERVICE_BOUNDARIES.md`;
   * `docs/stages/STAGE_03_REPORT.md`;
   * `docs/market_data/TIMESTAMP_CONTRACT.md`;
   * `docs/market_data/FEATURE_CONTRACT.md`;
   * действующие контракты Universe и Features;
   * действующие миграции Paper DB.

2. Проверить фактическое состояние `main`.

3. Сначала построить карту существующей реализации уровней и схемы БД.

4. Не копировать старую реализацию `monitor-data` без проверки её ошибок и несовместимостей.

5. Работать в отдельной ветке:

```text
stage/04-levels
```

Не выполнять merge и production-развёртывание без отдельного разрешения.

---

# 3. Архитектурные границы

Levels Builder:

```text
читает Universe
читает immutable Features
читает Market Data через SELECT-only Reader
строит уровни
обслуживает состояния уровней
строит проекцию близости цены к уровням
```

Levels Builder не зависит от:

```text
Scanner
Growth
Detector
сделок
балансов
сигналов
```

Запрещено:

```text
изменять monitor-data
писать в Market DB
открывать сделки
создавать Signal
создавать Candidate Scanner
изменять финансовые таблицы
смешивать Binance и Bybit
выдавать частично построенный набор
```

---

# 4. Общие правила данных

```text
только Decimal
float запрещён
явный timezone-aware as_of
UTC
только закрытые свечи
future rows исключаются
None не превращается в 0
одинаковая версия quality policy
одинаковый source cutoff внутри расчёта
```

Universe обрабатывать пакетами:

```text
не более 100 символов на запрос
```

Не запускать отдельный процесс на каждую монету.

---

# 5. Основа уровня

Базовая геометрия уровня строится только по:

```text
цене
+
объёму
```

Не участвуют в формировании границ:

```text
OI
funding
ликвидации
Scanner Candidates
Growth State
```

Эти данные позже могут быть добавлены как отдельный контекст, но не могут:

```text
создавать базовый уровень
передвигать zone_low или zone_high
удалять уровень
```

---

# 6. Разделение по биржам

У каждого уровня обязательно хранится:

```text
exchange
symbol
```

Уровень Binance никогда не объединяется и не подтверждается данными Bybit.

Даже при одинаковой монете уровни бирж считаются независимыми.

---

# 7. История

При первичном запуске построить уровни по всей доступной качественной истории.

Не ограничивать историю семью днями.

После первичного backfill использовать:

```text
часовое инкрементальное построение
минутное обслуживание активных зон
суточную контрольную сверку
```

Старый уровень не удаляется только из-за возраста.

---

# 8. Типы формирования

Поддержать два типа источника.

## 8.1 VOLUME_IMPULSE_LEVEL

Формируется отдельной закрытой часовой свечой с аномальным объёмом.

Минимальная кратность объёма:

```text
3× относительно обычного объёма монеты
```

## 8.2 VOLUME_CLUSTER_LEVEL

Формируется несколькими соседними закрытыми часовыми свечами, если повышенный объём концентрируется в общей ценовой области.

Минимальное количество свечей и максимальная длина кластера должны быть параметрами конфигурации.

Рекомендованные defaults v1:

```text
cluster_min_candles = 2
cluster_max_candles = 6
```

Алгоритм обязан сохранять исходные свечи и объяснять, почему они объединены.

---

# 9. Baseline объёма

Кратность формирования рассчитывать относительно обычного часового quote volume этой же монеты и этой же биржи.

Использовать versioned конфигурацию.

Рекомендованный default v1:

```text
baseline_method = median
baseline_window = предыдущие 24 закрытые часовые свечи
текущая свеча исключается
```

Хранить:

```text
formation_volume_usd
baseline_volume_usd
formation_volume_multiple
baseline_method
baseline_window
policy_version
```

Если baseline отсутствует или quote volume недоступен, уровень не создавать.

---

# 10. Формирование зоны

Уровень хранится диапазоном:

```text
zone_low
zone_high
center_price
zone_width_pct
```

Запрещено хранить торговый уровень только одной точной ценой.

Для формирования использовать минутные свечи внутри исходного часового окна или кластера.

Рекомендованный детерминированный алгоритм v1:

```text
typical_price = (high + low + close) / 3
вес = quote volume минутной свечи
center_price = volume-weighted median typical_price
zone_low = volume-weighted 20 percentile
zone_high = volume-weighted 80 percentile
```

Все формулы должны быть:

```text
документированы
версионированы
покрыты тестами
настраиваемы
```

Если минутные данные неполные или quote volume отсутствует, построение работает fail-closed.

Не подменять close значением `MAX(close)`.

# 12. Категории объёма формирования

```text
меньше 3×  → уровень не создаётся
3–5×       → NORMAL
5–10×      → STRONG
больше 10× → EXTREME
```

Хранить отдельно:

```text
formation_volume_multiple
formation_volume_class
```

Не заменять эти данные одним непрозрачным score.

---

# 13. Объединение близких зон

Новая зона объединяется с существующей только если:

```text
одинаковая биржа
одинаковая монета
зоны пересекаются
или расстояние между ними меньше merge threshold
```

`merge_gap_pct` должен быть параметром конфигурации.

Рекомендованный default v1:

```text
merge_gap_pct = 0.25%
```

Перед объединением проверить, что между зонами нет отдельной подтверждённой области концентрации объёма.

При объединении сохранить:

```text
все source events
самый ранний formed_at
последний formation_last_at
суммарный formation volume
максимальную volume multiple
историю реакций
историю статусов
```

Запрещено терять старые источники или молча переписывать уровень.

---

# 14. Значимость

Значимость определяется отдельными прозрачными показателями:

```text
formation_volume_multiple
initial_move_pct
touch_count
confirmed_reaction_count
failed_reaction_count
max_reaction_pct
average_reaction_pct
break_count
```

Категории:

```text
WEAK
NORMAL
STRONG
EXTREME
```

Причина категории должна быть доступна в данных.

Не использовать в v1 единый скрытый `level_score`.

---

# 15. Свежесть

Хранить:

```text
formed_at
last_confirmed_at
```

Дата свежести:

```text
freshness_at = max(formed_at, last_confirmed_at)
```

Категории:

```text
HOT    — до 7 дней
FRESH  — от 8 до 30 дней
AGED   — от 31 до 90 дней
OLD    — более 90 дней
```

Простое касание не обновляет свежесть.

Свежесть обновляется только после подтверждённой реакции или подтверждённого ретеста.

Старый уровень после новой значимой реакции снова становится свежим.

---

# 16. Текущая близость к уровню

Поддерживать отдельную изменяемую projection:

```text
exchange
symbol
level_id
current_price
distance_to_level_pct
price_position
updated_at
```

Состояния:

```text
ABOVE_LEVEL
BELOW_LEVEL
NEAR_LEVEL
TOUCHING_LEVEL
INSIDE_LEVEL
MOVED_AWAY
BROKEN_LEVEL
```

Начальный порог:

```text
NEAR_LEVEL = расстояние до зоны не более 5%
```

Порог хранить в конфигурации.

---

# 17. Минутная пакетная проверка

После закрытия каждой минутной свечи выполнить один пакетный расчёт, а не отдельный процесс для каждой монеты.

Логика:

```text
получить новые закрытые минутные свечи
соединить их с ACTIVE/RETESTED уровнями
отобрать уровни возле текущей цены
проверить реальные пересечения
обновить только найденные совпадения
```

Касание:

```text
candle_high ≥ zone_low
и
candle_low ≤ zone_high
```

Пример ожидаемой работы:

```text
1100 новых свечей
→ пакетная фильтрация
→ несколько десятков монет возле уровней
→ несколько реальных касаний
→ подробная обработка только касаний
```

---

# 18. Касание

При первом входе в зону сохранить:

```text
touch_id
level_id
touch_at
touch_price
touch_direction
touch_volume_usd
touch_volume_multiple
```

Обновить:

```text
last_touched_at
touch_count
```

Одно пребывание цены внутри зоны не должно каждую минуту увеличивать `touch_count`.

Новый touch начинается только после выхода цены из зоны и последующего нового входа.

Касание само по себе уровень не подтверждает.

---

# 19. Реакция

После касания отслеживать максимальное движение цены от границы зоны.

Категории:

```text
менее 3%  → слабая, уровень не подтверждает
3–5%      → NORMAL_REACTION
5–10%     → STRONG_REACTION
более 10% → EXTREME_REACTION
```

При реакции не менее 3%:

```text
confirmed_reaction_count += 1
last_confirmed_at обновляется
last_reaction_pct сохраняется
max_reaction_pct обновляется
average_reaction_pct пересчитывается
freshness обновляется
```

Если цена не дала подтверждённую реакцию:

```text
failed_reaction_count += 1
```

---

# 20. Объём при касании и реакции

Хранить как отдельный контекст:

```text
touch_volume_usd
touch_volume_multiple
reaction_volume_usd
reaction_volume_multiple
```

Объём при касании:

```text
не создаёт новый уровень
не передвигает зону
не подтверждает уровень без движения цены
```

Пример:

```text
касание + объём 7× + реакция 8%
→ сильное подтверждение

касание + объём 7× + реакции нет
→ подтверждения нет
```

---

# 21. Повторные реакции

Интерпретация:

```text
0 реакций   → непроверенный
1 реакция   → подтверждённый
2–3 реакции → сильный
4+ реакций  → часто тестируемый, возможно ослабевающий
```

Четыре касания не должны автоматически удалять уровень.

Хранить отдельно:

```text
touch_count
confirmed_reaction_count
failed_reaction_count
```

Detector позже решает, как использовать количество тестов.

---

# 22. Пробой

Один прокол тенью не считается пробоем.

Рекомендованное правило v1:

```text
три последовательные закрытые минутные свечи
закрылись за одной границей зоны
и не вернулись внутрь
```

Параметр:

```text
break_confirmation_candles = 3
```

При подтверждении:

```text
status = BROKEN
broken_at
break_direction
break_volume_multiple
break_count += 1
```

Пробитый уровень не удалять.

---

# 23. Ретест

После пробоя отслеживать возврат цены к зоне с противоположной стороны.

При подтверждённой реакции после ретеста:

```text
status = RETESTED
retested_at
retest_direction
retest_reaction_pct
last_confirmed_at обновляется
```

Пример:

```text
сопротивление пробито вверх
→ цена возвращается сверху
→ зона удерживает цену
→ уровень работает как поддержка
```

---

# 24. Статусы

```text
BUILDING
ACTIVE
BROKEN
RETESTED
INACTIVE
FAILED
```

Значения:

```text
BUILDING — набор или уровень рассчитывается
ACTIVE   — доступен детекторам
BROKEN   — подтверждённо пробит
RETESTED — подтверждён с другой стороны
INACTIVE — хранится, но не входит в актуальную выдачу
FAILED   — расчёт не завершён
```

Возраст сам по себе не переводит уровень в `INACTIVE`.

---

# 25. Слои выдачи

## ALL

Все найденные уровни и полная история.

## RELEVANT

Уровни с достаточным объёмом формирования или подтверждёнными реакциями.

## PRIORITY

Уровни, которые:

```text
находятся рядом с текущей ценой
имеют статус ACTIVE или RETESTED
являются свежими
имеют достаточную значимость
```

Не удалять уровни только ради ограничения количества.

Не применять жёсткое правило:

```text
выдать ровно 5, 10 или 20 уровней
```

---

# 26. Порядок приоритета

Порядок:

```text
1. HOT/FRESH и STRONG/EXTREME
2. HOT/FRESH средней значимости
3. AGED/OLD, но EXTREME с сильными реакциями
4. Старые слабые уровни
```

При выдаче Detector учитывать:

```text
расстояние
свежесть
значимость
status
сторону уровня
последнюю реакцию
количество тестов
```

Расстояние используется как фильтр актуальности, но не заменяет свежесть и значимость.

# 29. Частота обновления

## Каждую минуту

Пакетно:

```text
обновление distance_to_level_pct
NEAR_LEVEL
TOUCHING_LEVEL
INSIDE_LEVEL
выход из зоны
реакция
пробой
ретест
```

## Каждый час

После закрытия новой часовой свечи:

```text
поиск новых импульсных зон
поиск новых кластерных зон
объединение близких зон
обновление formation evidence
```

## Раз в сутки

Контрольное обслуживание:

```text
проверка всех сохранённых уровней
пересчёт freshness categories
пересчёт significance categories
поиск и объединение дублей
проверка статусов
проверка текущей READY projection
```

Полный повторный backfill всей Market DB выполнять:

```text
при первом запуске
при изменении policy version
при ручной команде rebuild
при обнаруженном расхождении
```

Не перечитывать всю многолетнюю историю ежедневно без необходимости.

# 30. Безопасное обновление наборов

Каждый расчёт имеет:

```text
run_id
exchange
as_of
policy_version
status
started_at
finished_at
```

Переход:

```text
BUILDING → READY
или
BUILDING → FAILED
```

Detector видит только последний полный `READY`-набор.

Если новый run завершился `FAILED`:

```text
предыдущий READY продолжает работать
```

Запрещено публиковать частично рассчитанный набор.

Для каждого exchange должен быть независимый run и независимый lock.

---

# 31. Идемпотентность

Повторная обработка одного:

```text
exchange
symbol
source window
policy version
```

не должна создавать новый дублирующий уровень.

При replay:

```text
источники совпали → результат совпал
checksum совпал → новая версия не создаётся
source correction изменила checksum → создаётся новая аудируемая версия
```

# 34. Критерии приёмки

Этап принимается только если:

```text
работают ровно два Levels-контейнера
уровни Binance и Bybit независимы
база уровня строится только по цене и объёму
используются зоны, а не одна цена
уровни строятся по широкой истории
новые зоны ищутся каждый час
касания обслуживаются пакетно каждую минуту
свежесть обновляется только реакцией
старые уровни не удаляются из-за возраста
нет непрозрачного общего score
Detector получает только READY
ошибка нового run не уничтожает старый READY
Market DB остаётся read-only
все тесты проходят
```
